# Проверка и починка шагов курса (команды из документации должны работать)

## Summary

Проверочный проход по существующему курсу из 17 шагов: пройти цепочку тегов `step-NN` по порядку, реально выполнить команды каждой главы для шагов 01–11, починить каждую ошибку в самом раннем шаге, где она возникает, и перестроить цепочку тегов вперёд — так, чтобы на каждом теге документированные команды и наблюдаемые результаты действительно сходились.

---

## Problem Frame

Курс (главы 00–16, стек-файлы, Dockerfile, наблюдаемость, multipass-скрипты) был сгенерирован целиком по плану и зафиксирован в 17 коммитах с тегами `step-00 … step-16` — но команды из документации, судя по всему, **ни разу не прогонялись end-to-end**. Читатель, который проходит главы по порядку (открыл шаг 01, затем 02, выполнил команды), упирается в ошибки.

Симптомы на текущем состоянии репозитория уже видны: HEAD в detached-состоянии на `step-01`, в рабочем дереве висят незакоммиченные правки `package.json` (бамп `@nestjs/core`/`platform-express` `^10 → ^11`, `@itgorillaz/configify` `^1.3.2 → ^4.1.2`, при этом `@nestjs/common` остался на `^10`). Сильно вероятный системный корень — дрейф версий: зафиксированные в шагах версии не совпадают с API, который показан в коде и главах (например, configify `^1.3.2` против v4-API `@Value('PORT', { parse, default })`; `common@10` против `core@11`).

Цена пробела: учебный курс не выполняет своё единственное обещание — «делай по главе и получишь описанный результат». Ошибки систематические (версии/окружение), а не разовые опечатки, поэтому их нужно вычистить связным проходом, а не точечно.

---

## Actors

- A1. Читатель курса: проходит главы по порядку, выполняет команды руками, ожидает ровно тот результат, что описан в главе. Бенефициар корректности — под него оптимизируется итоговая гарантия.
- A2. Сопровождающий (автор/агент): выполняет проверочный проход — прогоняет команды, находит и чинит ошибки, перестраивает цепочку коммитов и тегов.

---

## Key Flows

- F1. Проверка и починка одного шага
  - **Trigger:** переход к шагу N в перестраиваемой цепочке.
  - **Actors:** A2 (выполняет), ради A1 (для него — итоговый результат).
  - **Steps:** воссоздать состояние шага N поверх уже исправленных предыдущих → для 01–11 выполнить все команды главы N, для 12–16 вычитать главу → при ошибке починить в самом раннем шаге, где она появляется → продолжить перестройку цепочки поверх исправленного состояния → переустановить тег `step-NN`.
  - **Outcome:** на теге `step-N` команды главы дают документированный наблюдаемый результат (для 12–16 — глава командно-корректна по ревью).
  - **Covered by:** R1, R2, R3, R4, R6.

---

## Карта работы

    step-00 → step-01 → … → step-11        step-12 → … → step-16
    └────────── ВЫПОЛНЯЕМ ──────────┘      └──── ВЫЧИТЫВАЕМ ────┘
       (реальный прогон команд)              (ревью без VM-прогона)

    Фикс ошибки на шаге N  ──►  перестройка (rebase) всех шагов > N  ──►  пересоздание тегов step-N … step-16
    (ошибка чинится один раз в самом раннем шаге; правка распространяется вперёд по цепочке)

---

## Requirements

**Процесс проверки**
- R1. Пройти цепочку шагов по порядку; для каждого шага 01–11 воссоздать его состояние и выполнить **все** команды из соответствующей главы `docs/chapters/NN-*.md`.
- R2. Шаг считается проверенным, только когда каждая документированная команда отрабатывает успешно **и** сходится заявленный в главе наблюдаемый результат (например: `GET /` отдаёт hostname+версию; при нескольких репликах ответы показывают разные hostname; rolling update идёт без даунтайма; пароль БД не виден в образе/`inspect`/логах). Одного «exit 0» недостаточно.
- R3. Шаги 12–16 (multi-node) не выполняются на VM; вместо этого — вычитка на корректность: синтаксис команд, внутренняя согласованность, наличие упоминаемых файлов в теге, согласованность пинов версий/конфигов с исправленными ранними шагами. Найденные ошибки чинятся в том же проходе.

**Починка и история**
- R4. Каждая ошибка чинится в самом раннем шаге, где она возникает; правка распространяется вперёд через перестройку цепочки, а не дублируется в каждом шаге.
- R5. Когда документация и реальное поведение расходятся — чинится то, что отклонилось от учебного замысла: правится код/команда, если это настоящий баг; правится текст главы/ожидаемый вывод, если неточно само утверждение. Итог: заявленный в главе наблюдаемый результат должен стать правдой.
- R6. Фикс вносится перезаписью затронутого коммита и перестройкой (rebase) всех последующих коммитов поверх него с последующим пересозданием затронутых тегов `step-NN`. Текущая незакоммиченная правка `package.json` (и пересобранный lock-файл) вносится **в** `step-01`, а не остаётся на detached HEAD.
- R7. Так как история — одна линейная цепочка, после прохода пересоздаётся весь набор тегов `step-00 … step-16` — включая 12–16 — чтобы каждый тег отражал исправленное состояние.

**Итоговая гарантия**
- R8. По завершении: читатель, переключившись на любой `step-NN` (01–11) и следуя главе, выполняет каждую команду и получает документированный результат; главы 12–16 командно-корректны и внутренне согласованы по ревью.

## Acceptance Examples

- AE1. **Covers R1, R2.** Дано: `step-04` после фикса. Когда читатель выполняет команды главы 04 и шлёт серию запросов на `/`, ответы возвращают разные hostname — балансировка наблюдаема.
- AE2. **Covers R2, R5.** Дано: `step-01` после фикса. Когда выполняется `npm install && npm run start:dev` и `curl localhost:3000`, ответ совпадает с документированным `{"hostname":"…","version":"dev"}`, а пин версии configify соответствует API, использованному в главе.
- AE3. **Covers R4, R7.** Дано: дрейф версий configify/Nest, внесённый на `step-01`. Когда он починен на `step-01` и цепочка перестроена, все последующие теги (включая 12–16) ставят исправленные зависимости — баг починен один раз, а не в каждом шаге.
- AE4. **Covers R3.** Дано: `step-13` (multi-node, не выполняется). Когда глава вычитывается, каждая команда ссылается на файлы, существующие в этом теге, синтаксически корректна, а пины версий/конфигов согласованы с исправленными ранними шагами.
- AE5. **Covers R5.** Дано: глава документирует вывод, который код фактически не выдаёт. Когда шаг проверяется, либо правится код (настоящий баг), либо правится ожидаемый вывод в главе (неточное утверждение) — и после правки они сходятся.

---

## Success Criteria

- Читатель может переключиться на любой шаг 01–11, пройти главу, выполнить каждую команду и получить ровно документированный наблюдаемый результат — без сюрпризов и ручных обходов.
- Главы 12–16 командно-корректны и внутренне согласованы по ревью — готовы к проверке выполнением, когда появится multi-node окружение.
- Набор тегов `step-NN` целостен от начала до конца: каждый тег строится на предыдущем и отражает все фиксы; не остаётся orphaned/detached состояния.
- Downstream (`ce-plan`) может распланировать выполнение, не переоткрывая продуктовых решений: что значит «проверено», как далеко выполнять и как распространяются фиксы — уже зафиксировано.

---

## Scope Boundaries

- Автоматический doc-test harness/CI и ручной runbook — **за скобками**: это разовый проверочный проход (см. Outstanding Questions — возможный follow-up).
- Multi-node шаги (12–16) не выполняются и не поднимаются на VM — только вычитка.
- Не редизайн курса: без новых глав, без изменения педагогики, структуры и того, какой компонент вводится на каком шаге.
- Продуктовые non-goals из origin-требований остаются без изменений (реальный публичный TLS, облачный деплой, сравнение с Kubernetes, автоскейлинг/ротация секретов).
- Без апгрейда зависимостей сверх необходимого для работы документированных команд (никаких произвольных бампов версий «заодно»).

---

## Key Decisions

- **Фикс-в-источнике + перестройка цепочки + пересоздание тегов** (не 17 независимых правок коммитов): ранние фиксы распространяются вперёд, линейная история остаётся целостной.
- **Выполняем 01–11, вычитываем 12–16:** single-node надёжно прогоняется уже сейчас; multi-node проверка завязана на окружение (multipass + несколько VM) и отложена.
- **«Проверено» = сходится наблюдаемый результат, а не только exit 0:** ценность учебного курса — именно тот результат, который видит читатель.
- **Конфликт «док ↔ код» решается в сторону учебного замысла:** чиним настоящий баг либо правим неточное утверждение — по ситуации.
- **Разовый проверочный проход (без guardrail):** выбран ради низкой стоимости сопровождения; doc-test harness отмечен как возможный follow-up.

## Dependencies / Assumptions

- На dev-машине доступны Docker и Docker Swarm (single-node), Node 22 для приложения. (Docker 29.5 / Compose v5.1 / Node 22 — проверены в среде ранее.)
- Курс уже существует как коммиты с тегами `step-00 … step-16` на одной линейной истории; HEAD detached на `step-01`, в рабочем дереве — незакоммиченные правки `package.json`/lock-файла. (Проверено.)
- Вероятный системный корень — дрейф версий: зафиксированные пины против API в документации/коде (configify `^1.3.2` vs v4-API; Nest `common@10` vs `core@11`). (Сильно вероятно; подтверждается при выполнении.)
- Перестройка может давать конфликты rebase там, где поздние шаги тоже трогают общие файлы (`package.json` на step-05/08, stack-файлы) — это ожидаемо и решается по ходу прохода.
