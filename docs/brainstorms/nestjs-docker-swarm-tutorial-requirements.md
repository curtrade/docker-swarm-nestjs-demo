# Учебный проект: NestJS + Docker Swarm (пошагово, с best practices)

## Summary

Учебный репозиторий, который шаг за шагом учит разворачивать NestJS-приложение в Docker Swarm и доводит читателя до production-grade практик. Один эволюционирующий код-дерево растёт по одному сервису за раз через четыре тематических раздела; каждый шаг описан в нумерованной главе `docs/` и зафиксирован git-тегом запускаемого состояния. Материалы на русском.

---

## Problem Frame

Читатель уже умеет работать с Docker и `docker compose`, но не понимает, как от одиночного контейнера перейти к оркестрации: как развернуть сервис в кластере, масштабировать его, обновлять без даунтайма, безопасно прокидывать секреты и видеть, что реально происходит внутри. Большинство материалов по Swarm либо обрывочны (отдельные команды без связной картины), либо сразу вываливают сложный prod-стек без объяснения, почему каждая директива стоит на своём месте.

Цена этого пробела: оркестрацию осваивают методом проб на проде, копируя чужие stack-файлы без понимания; в результате — пароли в открытом виде, обновления с даунтаймом, нет наблюдаемости, узлы падают без понятного плана восстановления. Нужен связный путь, где каждая способность отрабатывается на запускаемом примере и объясняется построчно.

---

## Actors

- A1. Учащийся (читатель): проходит главы по порядку, выполняет шаги руками, наблюдает поведение Swarm. Основной актор — под него оптимизируется глубина объяснений и порог входа.

---

## Карта курса

| Раздел | Топология | Новый компонент | Ключевые темы Swarm |
|---|---|---|---|
| 1. Деплой и обновления без даунтайма | single-node | NestJS, Redis, Traefik | `stack deploy`, реплики, overlay, балансировка, healthcheck, rolling update + rollback |
| 2. Секреты и конфиги | single-node | Postgres | docker secrets / configs, без открытых паролей |
| 3. Наблюдаемость | single-node | Prometheus, Grafana | метрики, дашборды, логи, диагностика |
| 4. Capstone: кластер | multi-node (VM) | registry | join, placement, кворум, failover, drain |

Компоненты не вываливаются сразу — каждый вводится в тот момент, когда иллюстрирует конкретную тему оркестрации.

---

## Key Flows

- F1. Прохождение одного шага
  - **Trigger:** читатель открывает главу N в `docs/`.
  - **Actors:** A1.
  - **Steps:** читает объяснение и построчный разбор stack-файла → вносит изменения в код/стек → деплоит (`stack deploy` / `service update`) → наблюдает результат командами из главы → при необходимости сверяется с git-тегом `step-NN`.
  - **Outcome:** освоена одна тема, на руках — запускаемое состояние, совпадающее с тегом шага.
  - **Covered by:** R1, R2, R3.

---

## Requirements

**Структура и подача материала**
- R1. Репозиторий — git-репозиторий; на каждый завершённый запускаемый шаг ставится аннотированный git-тег (`step-NN`). Код живёт в одном эволюционирующем дереве, без папок-копий на шаг.
- R2. Объяснения — в нумерованных главах `docs/` (по одной на шаг) + README-оглавление с предпосылками и картой четырёх разделов. Каждый шаг воспроизводим: глава содержит команды запуска и наблюдаемый результат для самопроверки.
- R3. Каждый stack/compose-файл сопровождается построчным разбором (что делает директива и почему именно так), и каждая глава явно называет применённые best practices и анти-паттерны, которых избегаем (pinned-теги образов, healthcheck, restart policy, лимиты/резервы ресурсов, секреты вместо env).

**Базовое приложение NestJS**
- R4. Минимальный NestJS-сервис с поверхностью, делающей поведение Swarm наблюдаемым: endpoint, возвращающий hostname контейнера и версию (видно балансировку/реплики), и `/health` для healthcheck; позже добавляются Redis- и DB-зависимые endpoint'ы. Сборка — multi-stage Dockerfile по best practices (non-root, минимальный рантайм-образ, кэширование зависимостей).
- R5. Приложение следует конвенциям проекта: конфигурация через `@itgorillaz/configify`, доступ к Postgres через Prisma; разработка по TDD, с ESLint + Prettier.

**Раздел 1 — Деплой и обновления без даунтайма (single-node)**
- R6. Переход локальный `docker compose` → `docker swarm init` → первый `docker stack deploy`, с объяснением разницы между compose и stack.
- R7. Масштабирование сервиса до N реплик с наблюдаемой балансировкой запросов (через возвращаемый hostname); overlay-сеть и service discovery по имени сервиса.
- R8. Redis вводится как общее состояние: демонстрация, что in-memory состояние ломается при нескольких репликах, и перенос его в Redis. Traefik вводится как ingress/маршрутизатор к репликам (вместо «голого» published-порта), с self-signed TLS для обучения.
- R9. Healthcheck'и сервисов + restart policy (Swarm пересоздаёт упавшую реплику) и rolling update с настройкой `update-config` (parallelism / delay / order) и автоматическим rollback при сбое — обновление версии образа без даунтайма.

**Раздел 2 — Секреты и конфиги (single-node)**
- R10. Postgres вводится в этом разделе через арку «наивно → правильно»: сначала показывается соблазнительный подход с паролем БД через переменную окружения (и почему он плох — пароль виден в образе, стеке, `inspect`, логах), затем перевод на docker secret (монтируется как файл, не env).
- R11. NestJS читает секреты из файлов через Configify — паролей нет в открытом виде нигде в pipeline; несекретная конфигурация выносится в docker configs; формулируется принцип минимальной экспозиции (какому сервису какой секрет). Ротация секретов — за скобками, упоминается как «дальше».

**Раздел 3 — Наблюдаемость (single-node)**
- R12. Prometheus собирает метрики приложения (NestJS экспортирует `/metrics`), Traefik и узла; Grafana показывает дашборды: состояние сервисов, число и распределение реплик, latency/throughput, потребление ресурсов.
- R13. Централизованные логи сервисов; глава показывает, как по метрикам и логам диагностировать типовые проблемы (упавшая реплика, рост latency, нехватка ресурсов).

**Раздел 4 — Capstone: multi-node кластер (VM)**
- R14. Поднятие нескольких узлов локально на VM (manager + worker'ы), инициализация Swarm и присоединение узлов по join-token; локальный registry для раздачи образов на все узлы, с объяснением, почему на multi-node без registry образы не доедут до worker'ов.
- R15. Placement (constraints / preferences) и распределение реплик по узлам; роли manager/worker и кворум менеджеров (почему число менеджеров нечётное).
- R16. Отказоустойчивость и обслуживание: падение узла → переезд задач на живые узлы → восстановление узла; `docker node update --availability drain` для вывода узла без даунтайма. Полный стек предыдущих разделов (секреты + наблюдаемость) переносится на кластер и проверяется в работе.

## Acceptance Examples

- AE1. **Covers R7.** Дано: сервис в 3 реплики за overlay/Traefik. Когда читатель отправляет несколько запросов на `/`, ответы возвращают разные hostname — балансировка между репликами наблюдаема.
- AE2. **Covers R9.** Дано: запущенный стек версии v1. Когда выполняется деплой образа v2 с rolling update, внешние запросы продолжают обслуживаться без ошибок (нулевой даунтайм); при намеренно «битой» v2 срабатывает автоматический rollback к v1.
- AE3. **Covers R4, R9.** Дано: сервис с healthcheck. Когда реплику убивают, Swarm пересоздаёт её и сервис возвращается к заданному числу реплик.
- AE4. **Covers R10, R11.** Дано: стек после Раздела 2. Когда читатель инспектирует образ, stack-файл, переменные окружения и логи, пароль БД нигде не виден в открытом виде — только как смонтированный секрет-файл.
- AE5. **Covers R16.** Дано: 3-узловой кластер с распределёнными репликами. Когда один worker выключается, его задачи переезжают на живые узлы и сервис остаётся доступен; при возврате узла нагрузка может перераспределиться.

## Success Criteria

- Прочитав проект целиком, человек уверенно делает руками все четыре целевые вещи: разворачивает стек и обновляет его без даунтайма, понимая каждую строку stack-файла; прокидывает секреты и конфиги без открытых паролей; снимает метрики и логи и диагностирует проблему; поднимает multi-node кластер, переживает падение узла и обслуживает узел через `drain`.
- Любой шаг запускается «с нуля» по инструкции из главы на чистой машине и даёт описанный наблюдаемый результат; git-теги соответствуют главам.
- Downstream (`ce-plan`) может распланировать сборку без додумывания продуктового поведения: состав и порядок разделов, целевые наблюдаемые результаты и проектные конвенции зафиксированы.

## Scope Boundaries

- CI/CD-пайплайн (автоматическая сборка и публикация образов) — за скобками.
- Реальный публичный TLS (Let's Encrypt, реальный домен) — за скобками; для обучения используется self-signed.
- Бэкап/восстановление и стратегии миграции данных Postgres сверх базового — за скобками.
- Облачный деплой (узлы в облаке, managed-инфраструктура) — только локально: single-node + локальные VM.
- Сравнение и миграция на Kubernetes — за скобками.
- Автоскейлинг и автоматическая ротация секретов — за скобками (упоминаются как направление «дальше»).

## Key Decisions

- Полный стек, накапливаемый по одному сервису: каждый компонент вводится тогда, когда иллюстрирует конкретную тему Swarm — иначе фокус обучения размывается.
- Multi-node — финальный capstone, а не сквозной режим: разделы 1–3 идут на single-node ради низкого порога входа; кластер на VM включается только в конце.
- Эволюционирующий репозиторий + git-теги (а не папка-на-шаг): видна разница между шагами через diff, меньше дублирования.
- Гибридная топология: основной трек на single-node, продвинутый раздел — на реальных VM.
- Конвенции проекта (Configify, Prisma, TDD) применяются и в учебном коде, чтобы приложение было реалистичным, а не игрушечным.
- Арка «наивно → правильно» для секретов (env-пароль в Разделе 2 → docker secret) — намеренный учебный приём, делающий ценность секретов осязаемой.

## Dependencies / Assumptions

- На машине доступны Docker (29.5) и Docker Compose (v5.1); Node 22 для локальной разработки. (Проверено в среде.)
- Для capstone нужен инструмент локальных VM (по умолчанию multipass); машина должна потянуть несколько VM одновременно.
- Registry для multi-node — локальный registry-сервис в Swarm (по умолчанию), без внешнего реестра.
- Читатель уже владеет Docker и `docker compose`.
- Материалы, комментарии и главы — на русском.
