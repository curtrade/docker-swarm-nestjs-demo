# fix: Проверка и починка шагов курса (команды документации работают на своих тегах)

## Summary

Перестроить линейную историю курса (`main` = `step-00 … step-16` + хвостовые коммиты) так, чтобы команды каждой главы реально работали на соответствующем теге. Идём по цепочке с самого начала, чиним каждую ошибку в самом раннем шаге, где она возникает, выполняем и проверяем шаги 01–11 на single-node, вычитываем 12–16 без запуска, перераспределяем хвостовой фикс по «родным» шагам, переустанавливаем 17 тегов и `main`, и публикуем force-push'ем.

---

## Problem Frame

Курс сгенерирован целиком и зафиксирован в истории `main`, но команды документации, судя по всему, **не прогонялись end-to-end** — читатель, идущий по главам, упирается в ошибки. Подробный разбор мотивации — в origin-документе (см. Sources & References). План отвечает на «как починить и гарантировать», а не «зачем».

Состояние репозитория на момент планирования (проверено):

- `main` = `feat/nestjs-docker-swarm-tutorial` = `origin/main` = `b9f4057` — **19 коммитов**: `step-00 … step-16` (17) плюс два нетегированных хвостовых: `5bab368` (chore: пометить план completed) и `b9f4057` (fix, сваленный в хвост: ошибочные ответы и кардинальность меток в метриках, лог ошибок Prisma, коммент к tsconfig).
- HEAD — detached на `step-01`; в рабочем дереве висит незакоммиченная правка `package.json` (бамп версий) — это начатый фикс дрейфа версий, который должен попасть **в** `step-01`.
- История строго линейна (`step-00 → … → step-16 → 5bab368 → b9f4057`); `step-16` — предок `main`.
- Хвостовой фикс `b9f4057` НЕ трогает `package.json`; его правки относятся к метрикам (≈ step-10), Prisma (≈ step-08) и tsconfig (≈ step-01) — все внутри диапазона выполнения 01–11.

Это и есть антипаттерн, который курс должен искоренять: фиксы свалены в хвост вместо тех шагов, где они нужны.

## Key Technical Decisions

- **Cherry-pick-реплей вместо `rebase -i`:** интерактивный rebase недоступен в среде агента. Цепочка перестраивается последовательным переносом исходных коммитов шагов поверх исправленного предшественника с правкой на месте; теги переустанавливаются по мере финализации каждого шага.
- **Фикс-в-источнике + распространение вперёд:** ошибка чинится один раз в самом раннем шаге; перестройка несёт правку во все последующие. Это покрывает и дрейф версий (`step-01`), и перераспределение хвостового фикса.
- **Перераспределение `b9f4057` (подтверждено пользователем):** правки хвоста разносятся по «родным» шагам — метрики/тест → step-10, Prisma-фильтр → step-08, коммент tsconfig → step-01 — а не остаются в хвосте. После перераспределения хвостовой fix-коммит исчезает.
- **`5bab368` (completed-marker):** правит другой план-документ; сохраняется как хвостовой housekeeping-коммит поверх перестроенной цепочки.
- **Перезапись опубликованной истории + force-push (подтверждено пользователем):** после перестройки `main`/`feat` переводятся на новый tip, теги переустанавливаются, публикация — `git push --force-with-lease` для ветки и тегов.
- **Сеть безопасности обязательна:** перед переписыванием создаются backup-ref'ы текущего состояния (`main`, `feat`, все `step-*`); удаляются только после подтверждения целостности. Force-push — `--force-with-lease`, не `--force`.
- **«Проверено» = сходится наблюдаемый результат** (R2): для инфраструктурных шагов — наблюдаемый эффект (разные hostname, zero-downtime, пароль не виден), для кода — зелёные Jest + документированный вывод.
- **Глубина выполнения:** 01–11 выполняются на single-node; 12–16 перестраиваются и переустанавливаются (наследуют фиксы), но проверяются вычиткой, не запуском.

## High-Level Technical Design

> *Иллюстрирует целевую форму решения и является направляющим ориентиром для ревью, а не спецификацией реализации.*

```
ДО (опубликовано):
  step-00 → 01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10 → 11 → 12 → 13 → 14 → 15 → 16 → 5bab368 → b9f4057(main)
                                                          ▲(Prisma)        ▲(метрики)            └ хвостовой fix свален в конце
  + detached HEAD на step-01 с незакоммиченным package.json (дрейф версий)

ПОСЛЕ (перестроено):
  step-00 → 01' → 02' → … → 11' → 12' → … → 16' → 5bab368'(main')
             │                                     теги step-00..16 → на штрихованные коммиты
             ├─ fold: package.json/lock (дрейф версий) + коммент tsconfig
   step-08' ─┤─ fold: Prisma-фильтр (из b9f4057)
   step-10' ─┘─ fold: метрики + e2e (из b9f4057)
   ВЫПОЛНЯЕМ 01–11 (single-node)          ВЫЧИТЫВАЕМ 12–16 (без VM)
   b9f4057 растворён; backup-ref'ы держим до подтверждения; затем force-push --force-with-lease
```

Каждый шаг финализируется (коммит + перенос тега) по мере прохождения; «починка» и «перестройка» — одно действие, выполняемое по шагам.

## Implementation Units

Юниты сгруппированы в фазы. U-ID стабильны. Спина работы — линейный ре-walk; каждый юнит продвигает его через диапазон шагов, фиксируя и переустанавливая теги по ходу.

### U1. Каркас реплея, сеть безопасности и стратегия перестройки

**Goal:** До любого переписывания истории — зафиксировать механизм и откат. Создать backup-ref'ы текущих `main`/`feat`/всех `step-*`. Определить cherry-pick-реплей (без `rebase -i`), per-step verify-loop, политику пересборки lock-файла и финальную последовательность переноса тегов/веток + force-push. Начать рабочую ветку от неизменного `step-00`.

**Requirements:** R4, R6, R7 (механизм; поддерживает все)

**Dependencies:** None

**Files:**
- Create (опц.): `scripts/replay-steps.sh` (вспомогательный реплей; допустимо обойтись)
- Refs (не файлы): backup-ref'ы `backup/main`, `backup/feat`, `backup/step-NN`; рабочая ветка от `step-00`

**Approach:**
- Снять backup-ref'ы всего, что будет переписано; задокументировать процедуру отката (восстановление `main`/тегов из backup).
- Зафиксировать стратегию: cherry-pick исходного коммита шага → правка на месте (`commit --amend` или добавочные правки) → перенос тега `step-NN`.
- Политика lock-файла: пересобирать `package-lock.json` на шагах, где меняются зависимости, иначе нести как есть (см. Open Questions).

**Execution note:** Сначала «сухой» прогон step-00→step-01 без правок — убедиться, что реплей воспроизводит состояние чисто, прежде чем вносить фиксы.

**Test scenarios:**
- Test expectation: none — тулинг/безопасность. Проверка: backup-ref'ы существуют; откат восстанавливает `main`; «сухой» реплей даёт дерево, идентичное оригиналу на step-01.

**Verification:** backup-ref'ы на месте; рабочая ветка собирается на baseline; процедура отката проверена.

## System-Wide Impact

- **Interaction graph:** перестройка касается всей истории `main` и всех тегов `step-*`; downstream — `origin/main` (force-push) и любые существующие клоны/worktree'ы.
- **Контракт приложения не меняется:** REST-поверхность (`/`, `/health`, `/metrics`, `notes`, счётчик) и схема `notes` сохраняются — чиним конфигурацию/версии/доки, а не поведение продукта.
- **Распространение фиксов:** правка в раннем шаге наследуется всеми последующими через реплей — единый источник истины на каждый класс ошибки.
- **State lifecycle:** теги — единственное «состояние шага»; их перенос атомарен на финале (U7), не по ходу публикации.
- **Необратимость публикации:** force-push переписывает опубликованную историю — backup-ref'ы и `--force-with-lease` обязательны.

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| Force-push переписывает опубликованный `main` — ломает чужие клоны/worktree'ы | Подтверждено пользователем; `--force-with-lease`; backup-ref'ы; публикация только после полной проверки (U7). |
| Реплей даёт конфликты там, где поздние шаги тоже трогают общие файлы (`package.json` на 05/08, stack-файлы, метрики на 10) | Ожидаемо; разрешать по ходу; «сухой» прогон в U1 калибрует механизм. |
| Перераспределённый хвостовой фикс попадёт не в тот шаг / потеряется | U7 проверяет полноту: diff старый-tip ↔ новое состояние должен быть пуст, кроме намеренного. |
| Среда не тянет полный стек наблюдаемости (10–11) на single-node | Уменьшить реплики; лимиты ресурсов; при нехватке — пометить шаг как проверенный частично и вынести остаток в Deferred. |
| Интерактивный `rebase -i` недоступен в среде агента | Cherry-pick-реплей (Key Decisions); точная хореография — Open Questions. |
| Дрейф версий глубже, чем `package.json` (несовместимость API configify v4 / Nest 11) | U2 — корневой шаг; verify-then-fix вскроет несовместимости до распространения вперёд. |
| Потеря незакоммиченной in-flight правки `package.json` | U1 снимает backup рабочего дерева/ref'ов до начала; правка осознанно вкладывается в `step-01` (U2). |

**Dependencies / Prerequisites:**
- Docker + Docker Swarm (single-node), Node 22 — на dev-машине (проверено: Docker 29.5 / Compose v5.1 / Node 22).
- Доступ на push в `origin` (force-with-lease).
- multipass / несколько VM **не нужны** (12–16 не выполняются).
