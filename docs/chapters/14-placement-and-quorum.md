# Глава 14. Placement и кворум

> Тег шага: `step-14` · Часть 4 (capstone, multi-node)

## Цель

Управлять тем, **где** в кластере запускаются задачи: распределять stateless-реплики
по узлам, а stateful-сервисы закреплять на нужном узле. И разобраться с кворумом
менеджеров.

## Constraints против preferences

- **constraints** — жёсткое условие: задача запустится только на узле,
  удовлетворяющем правилу.
- **preferences** — мягкое: планировщик старается равномерно распределить.

### Закрепление stateful-сервисов (constraints)

Postgres и Redis используют **node-local volume** — данные лежат на диске того
узла, где запущена задача. Если задача переедет на другой узел, она увидит пустой
том. Поэтому закрепляем их:

```yaml
postgres:
  deploy:
    placement:
      constraints:
        - node.role == manager   # всегда на узле с данными
```

> В проде вместо «прибивания к узлу» используют сетевые/реплицируемые тома
> (например, плагины volume) или ставят БД вне Swarm. Здесь — простейший рабочий
> вариант для обучения.

### Распределение реплик (preferences)

Stateless `api` хотим равномерно «размазать» по узлам:

```yaml
api:
  deploy:
    replicas: 4
    placement:
      preferences:
        - spread: node.id   # по одной-две на узел, а не кучей
```

Проверка распределения:

```bash
docker service ps part4_api --format '{{.Name}} {{.Node}} {{.CurrentState}}'
# реплики раскиданы по swarm-manager / swarm-worker1 / swarm-worker2
```

### Произвольные метки узлов

Можно метить узлы и таргетировать по меткам — типичный приём для «узлов с SSD»,
«GPU-узлов», зон:

```bash
docker node update --label-add storage=true swarm-manager
# constraints: [ node.labels.storage == true ]
```

## Кворум менеджеров

Менеджеры хранят состояние кластера через **Raft** — для согласия нужен **кворум**
(большинство). Отсюда правило про **нечётное** число менеджеров:

| Менеджеров | Кворум | Переживают отказ |
|---|---|---|
| 1 | 1 | 0 (потеря управления) |
| 3 | 2 | 1 |
| 5 | 3 | 2 |

Чётное число бессмысленно: 4 менеджера переживают столько же отказов (1), сколько
и 3, но риск потерять кворум выше. Поэтому 3 или 5.

Добавить менеджера:

```bash
docker swarm join-token manager      # на действующем менеджере — получить токен
docker swarm join --token <manager-token> <MANAGER_IP>:2377   # на новом узле
```

> Важно: при потере кворума кластер продолжает **выполнять** задачи, но
> **управлять** им (деплой, масштабирование) нельзя, пока кворум не восстановлен.

## Best practices и анти-паттерны

- ✅ **Stateful — на закреплённый узел** (или сетевой том), не «гуляет» по кластеру.
- ✅ **Stateless — `spread`** по узлам для отказоустойчивости и баланса нагрузки.
- ✅ **Нечётное число менеджеров** (3/5) для кворума.
- ✅ **Метки узлов** для осмысленного таргетинга.
- ❌ **Не** держи на worker'ах stateful-сервис с локальным томом без закрепления —
   переезд = потеря данных.
- ❌ **Не** делай все узлы менеджерами «на всякий случай» — это расширяет
   поверхность согласования и риск.
