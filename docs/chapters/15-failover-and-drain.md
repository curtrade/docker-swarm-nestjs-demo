# Глава 15. Failover и drain

> Тег шага: `step-15` · Часть 4 (capstone, multi-node)

## Цель

Увидеть отказоустойчивость вживую: убить узел и посмотреть, как Swarm переселяет
задачи. Затем — корректно вывести узел на обслуживание через `drain`.

## Failover: падение узла

Допустим, `api` распределён по узлам (глава 14). Смотрим текущее размещение:

```bash
docker service ps part4_api --format '{{.Name}} {{.Node}} {{.CurrentState}}'
```

Останавливаем один worker (имитация отказа):

```bash
multipass stop swarm-worker1
```

Что происходит:

```bash
docker node ls                 # swarm-worker1 -> Down
docker service ps part4_api    # его задачи -> Shutdown, новые задачи Running на живых узлах
```

Swarm замечает, что узел недоступен, и **пересоздаёт** его задачи на оставшихся
узлах, чтобы вернуть заданное число реплик. Сервис всё это время доступен через
Traefik — запросы идут на живые реплики.

> Это и есть **AE5**: при отказе узла его задачи переезжают, сервис остаётся
> доступен.

Возвращаем узел:

```bash
multipass start swarm-worker1
docker node ls                 # снова Ready
```

Swarm **не** автоматически «возвращает» задачи на воскресший узел (нет ребаланса
по умолчанию). Принудительно перераспределить можно:

```bash
docker service update --force part4_api   # пересоздаст задачи, учитывая spread
```

## Drain: плановое обслуживание

Чтобы обновить узел (ядро, Docker) без потери доступности — переводим его в `drain`:

```bash
docker node update --availability drain swarm-worker2
docker node ls                 # swarm-worker2 -> Drain
docker service ps part4_api    # задачи уехали с worker2 на другие узлы
```

В состоянии `drain` узел **не принимает** новые задачи и с него **снимаются**
текущие. Делаем обслуживание, затем возвращаем:

```bash
docker node update --availability active swarm-worker2
```

Разница с «падением»: `drain` — управляемый, задачи снимаются аккуратно, без окна
недоступности (особенно вместе с `start-first` из главы 07).

## Что со stateful

Postgres/Redis закреплены на менеджере (глава 14). Если «упадёт» узел с ними —
задачи **не** переедут (некуда: том только там). Поэтому для БД в проде —
реплицируемое хранилище, реплики БД или вынос за пределы Swarm. Для stateless
(`api`) переезд бесшовный.

## Best practices и анти-паттерны

- ✅ **`drain` перед обслуживанием** — управляемое снятие задач, без даунтайма.
- ✅ **`spread` + несколько реплик** — отказ узла не роняет сервис.
- ✅ **`--force` для ребаланса** после возврата узла.
- ❌ **Не** рассчитывай на автоматический переезд stateful с локальным томом —
   данные привязаны к узлу.
- ❌ **Не** обновляй узлы «жёстким» выключением, если есть `drain`.
