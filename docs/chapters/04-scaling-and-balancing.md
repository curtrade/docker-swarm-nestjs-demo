# Глава 04. Масштабирование и балансировка

> Тег шага: `step-04` · Часть 1 (single-node)

## Цель

Масштабировать сервис до нескольких реплик и **увидеть балансировку** —
запросы должны распределяться между репликами.

## Два способа масштабирования

**1. Декларативно** — меняем `replicas` в stack-файле и передеплоиваем (так в репо):

```yaml
deploy:
  replicas: 3
```

```bash
docker stack deploy -c deploy/stacks/stack.part1.yml part1
```

**2. Императивно** — на лету, без правки файла:

```bash
docker service scale part1_api=3
```

Декларативный способ предпочтителен: состояние зафиксировано в файле под git,
а не «висит» в кластере незаписанным.

## Наблюдаем балансировку

```bash
docker stack services part1          # REPLICAS -> 3/3
docker service ps part1_api          # три задачи Running

# Несколько запросов — разные hostname (= разные реплики):
for i in $(seq 1 6); do curl -s localhost:3000 | grep -o '"hostname":"[^"]*"'; done
```

Ожидаемый вывод — чередующиеся id контейнеров, например:

```
"hostname":"a1b2c3d4e5f6"
"hostname":"f6e5d4c3b2a1"
"hostname":"a1b2c3d4e5f6"
...
```

Это и есть **routing mesh**: опубликованный порт (`mode: ingress`) принимает
соединения на любом узле и раскидывает их по живым задачам сервиса (L4,
round-robin на уровне соединений).

## Overlay и service discovery

Реплики и другие сервисы общаются по имени сервиса внутри overlay-сети `appnet`:
Swarm даёт встроенный DNS, и `api` резолвится в виртуальный IP (VIP), за которым
стоят все задачи. В главе 05 мы используем это, чтобы приложение нашло Redis по
имени `redis`.

## Best practices и анти-паттерны

- ✅ **Декларативные реплики** в stack-файле под git.
- ✅ **Stateless-реплики** — любая реплика обрабатывает любой запрос (поэтому в
   ответе и «гуляет» hostname). Состояние выносим наружу (глава 05).
- ✅ **Обращение по имени сервиса** вместо хардкода адресов.
- ❌ **Не** храни состояние в памяти реплики (сессии, счётчики) — при нескольких
   репликах оно рассыпется. Именно это «сломаем и починим» в следующей главе.
