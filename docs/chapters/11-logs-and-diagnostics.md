# Глава 11. Логи (Loki) и диагностика

> Тег шага: `step-11` · Часть 3 (single-node) — завершает Часть 3

## Цель

Собрать логи всех сервисов в одно место (Loki) и в той же Grafana, где метрики,
научиться диагностировать типовые проблемы по метрикам + логам.

## Loki + Promtail

- **Loki** — хранилище логов (как «Prometheus для логов»). Минимальная
  single-binary конфигурация с файловым хранилищем.
- **Promtail** — агент сбора: через docker socket обнаруживает контейнеры на узле
  и шлёт их stdout/stderr в Loki. Развёрнут `mode: global` — по одному на узел.

В Grafana добавлен второй datasource — **Loki**, так что метрики и логи в одной
панели (единое окно наблюдения).

```yaml
promtail:
  command: ['-config.file=/etc/promtail/promtail-config.yml']
  volumes:
    - /var/run/docker.sock:/var/run/docker.sock:ro   # обнаружение контейнеров
  deploy:
    mode: global
```

В метки логов кладём имя контейнера и имя Swarm-сервиса — по ним удобно
фильтровать в Grafana Explore: `{service="part3_api"}`.

## Проверка

```bash
docker stack deploy --resolve-image=never -c deploy/stacks/stack.part3.yml part3

# Grafana -> Explore -> datasource Loki -> запрос:
#   {service="part3_api"}
# Увидишь логи всех реплик api в одном потоке.
```

## Диагностика типовых проблем

Теперь у нас есть метрики (глава 10) и логи (эта глава). Разберём сценарии:

**1. Упавшая реплика.**
- Метрика: `up{job="api"}` < числа реплик; в дашборде «живых реплик» проседает.
- Логи: `{service="part3_api"}` покажут стек ошибки перед рестартом.
- Swarm: `docker service ps part3_api` — задача в состоянии `Failed`/`Restarting`.

**2. Рост latency.**
- Метрика: rate ошибок (`http_requests_total{status=~"5.."}`) растёт; CPU из
  cAdvisor у `api`/`postgres` упирается в лимит.
- Логи: медленные запросы, таймауты соединений к БД/Redis.
- Вывод: упёрлись в лимит ресурсов (глава 07) — поднять лимиты или число реплик.

**3. Нехватка ресурсов узла.**
- Метрика: node-exporter — память/CPU узла на пределе.
- Swarm: новые задачи висят в `Pending` (нет узла, удовлетворяющего
  reservations) — прямая дорога к Части 4 (несколько узлов).

## Best practices и анти-паттерны

- ✅ **Единое окно** (Grafana: метрики + логи) — быстрее находить причину.
- ✅ **Метки `service`/`container`** на логах — точная фильтрация.
- ✅ **Promtail как global-агент** — собирает логи со всех узлов.
- ✅ **Структурные логи** приложения (JSON) упрощают парсинг (направление для
   развития).
- ❌ **Не** полагайся только на `docker service logs` в проде — при пересоздании
   задач история теряется; для этого и нужен Loki.
- ⚠️ Хранение логов здесь короткое (`retention 72h`) и на одном узле — для обучения
   ок, для прода нужно объектное хранилище и продуманный retention.
